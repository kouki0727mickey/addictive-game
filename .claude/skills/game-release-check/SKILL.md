# ゲームの公開前チェック

ナレッジベースの基準で点検し、**直すべきもの・確認が要るもの・問題ないもの**を分けて報告する。日本語で書く。法的助言ではないことを冒頭に明記する。

## 0. ナレッジの場所を確かめる
`knowledge/` がなければ `git clone --depth 1 https://github.com/kouki0727mickey/addictive-game /tmp/ai-ent-kb` して読む。

## 1. ゲームを把握する
ゲームの README・設定・コード（課金、報酬、通知、デイリー・連続ログイン、ランキング、セーブ、AI呼び出し、生成アセット）を読み、次を洗い出す。分からない点は「要確認」にする。
- 配信先（Web / App Store / Google Play / Steam）と地域、対象年齢
- AIの使いどころ: 開発の道具だけか / ゲーム内の素材（絵・声・音楽・文章）か / プレイ中の生成（会話NPCなど）か
- 課金・広告・報酬・続ける仕掛けの一覧

## 2. 点検する項目と根拠
| 区分 | 見ること | 根拠 |
|---|---|---|
| 健全性 | 判定表6項目、レッドライン4つ、グリーンパターン、長時間・深夜の区切り、連続ログイン報酬が「失いたくない」だけに頼っていないか | `knowledge/foundations/engagement-design.md` |
| 指標 | 健全性の指標を計測しているか | 同上「指標設計」 |
| AI開示 | 使った工程の棚卸し、4点セット（どこに・なぜ・人は何をしたか・同意と権利）、開示の時期と場所 | `knowledge/foundations/ai-disclosure-guide.md` |
| ストア | Steam の生成AI申告（素材とランタイム生成。開発効率化だけのAIは不要）。他ストアはその時点の規約を一次情報で確認 | `knowledge/domains/games.md` |
| 国別法規制 | 配信地域ごとのAI表示（EU 50条・中国・韓国）、AIコンパニオン（NY州・カリフォルニア州・中国）、未成年 | `knowledge/ethics-legal/by-country/` |
| 声・肖像 | 実在の人に似せた声・姿がないか、許諾と契約 | `by-country/japan.md`、`knowledge/ai-characters/patterns.md` P38 |
| 会話NPC（あれば） | evaluation.md のリリース判定ゲート、攻撃テストの結果、コスト上限 | `knowledge/ai-characters/evaluation.md`、`/game-ai-character` |
| 個人データ | 会話ログ・記憶の保存期間、削除手段、年齢確認 | `by-country/` の各国、P33 |

- 各国の要件は記事の `last_reviewed` と施行日を確認する。記事が古い、または配信地域が記事にない場合は「要確認（一次情報で確かめる）」とする
- ゲームにAIを使っていない項目は「該当なし」と書き、理由を添える

## 3. 報告書の構成
出力先: このリポジトリなら `studio/<プロジェクト名>/release-check-YYYY-MM-DD.md`、ゲーム本体のリポジトリなら `docs/ai-design/release-check-YYYY-MM-DD.md`。

```markdown
# <タイトル> 公開前チェック（YYYY-MM-DD）
> ⚠️ 一般的な情報整理であり、法的助言ではない。点検の基準: <記事と last_reviewed>
> 対象: <バージョン / コミット>、配信先: <ストア・地域>、対象年齢: <>

## 結論
  - 直すべきもの N件 / 確認が要るもの N件 / 問題なし N件

## 直すべきもの
| # | 項目 | 見つかったこと（ファイル・行） | 直し方 | 根拠 |

## 確認が要るもの
| # | 項目 | 何を誰に確認するか | 根拠 |

## 問題なし・該当なし
| 項目 | 理由 |

## 開示文の案
  - ストアページ用・作品内（クレジット）用。ai-disclosure-guide の「○ 受け入れられやすい」例に沿う
```

## 4. 守ること
- 「問題なし」は、根拠となる記事の基準に照らして言えることだけにする。断定できないものは「確認が要るもの」に入れる
- コードは直さない（ユーザーが頼んだ場合だけ直す）
- 点検で見つかった一般化できる学び（例: よくある見落とし）は、ナレッジへの追加を最後に一言提案する
