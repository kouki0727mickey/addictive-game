# ゲーム企画書を作る（AI × ゲーム）

ナレッジベースの知見を根拠に、**遊んで面白く、健全で、コストが成り立つ**企画にする。日本語で書く。

## 0. ナレッジの場所を確かめる
- 作業中のリポジトリに `knowledge/` があればそれを使う
- なければ `git clone --depth 1 https://github.com/kouki0727mickey/addictive-game /tmp/ai-ent-kb` し、`/tmp/ai-ent-kb/knowledge/` を読む

## 1. 入力を確認する
ユーザーの依頼から次を読み取る。足りないものは、妥当な仮定を置いて企画書に「前提」として書く（止まって質問しすぎない）。
- 新作か、既存ゲームへの機能追加か（既存なら、そのゲームの README・コードを読み、コアループと既存の「続ける仕掛け」を把握する）
- ジャンル、対象プレイヤー（年齢層を含む）、プラットフォーム（Web / iOS / Android / Steam）、配信地域
- 予算・チーム規模・期間の目安

## 2. 読む記事
必ず読む:
- `knowledge/foundations/engagement-design.md`（動機の理論、ループ構造、健全/不健全の判定、レッドライン、指標）
- `knowledge/foundations/ai-native-entertainment.md`（7原則と体験の類型）
- `knowledge/domains/games.md`（制作・プレイ・運営でのAI、落とし穴）
- `knowledge/business/business-models.md`（収益モデル、ユニットエコノミクス）
内容に応じて読む:
- 会話NPC・AIキャラを含む → `knowledge/ai-characters/README.md`、`patterns.md`
- 物語が中心 → `knowledge/domains/interactive-story.md`
- 生成アセット（絵・声・音楽）を使う → `knowledge/foundations/ai-disclosure-guide.md`、`knowledge/domains/case-studies.md`

## 3. 企画書の構成
出力先: このリポジトリなら `studio/<プロジェクト名>/concept.md`、ゲーム本体のリポジトリなら `docs/ai-design/concept.md`。

```markdown
# <タイトル> 企画書
> 前提: <ジャンル / 対象 / プラットフォーム / 地域 / 規模>。根拠にしたナレッジ: <記事・パターン番号>

## 一言で言うと
## コアループ（AIを外しても触って楽しいか）
## AIの役割
| 機能 | AIがやること | ルールとして固定すること（コード側） | 根拠 |
  - 「ルールはコード、言葉はAI」（ai-native 原則2）、「事実はエンジンが持つ」（P16）に沿っているか
  - AIでなければ成立しない体験か、従来手法で足りるか（足りるなら従来手法を選ぶ）
## ハマる仕組み（動機とループ）
  - 有能感・自律性・関係性のどれに効くか。短期・中期・長期のループ
## 健全性の自己点検
  - engagement-design の判定表6項目に答える。レッドラインに当たる要素がないこと
  - 長時間プレイの区切り、未成年への配慮
## 指標（KPI）
  - 継続・質・健全性・収益を1つ以上ずつ。「通知なしの自発的再訪率」を入れる
## コストとモデル選び
  - 1プレイヤー・1日あたりの推論回数と費用の見積もり、上限到達時の挙動（P34、P37）
## 権利・開示・法務の論点
  - 生成アセットの有無、ストアの申告（Steam のランタイム生成など）、配信地域の要件 → 公開前は `/game-release-check`
## リスクと検証計画
  - 一番危ない仮説と、それを最小コストで確かめる方法（プロトタイプ、APIなしのテスト）
## 分かっていないこと
```

## 4. 書き方のルール
- 提案ごとに根拠（記事名・パターン番号・事例番号）を添える。ナレッジにない事実は出典を付けるか `【要確認】`
- 仮説は 💡 を付ける
- レッドライン（孤独・罪悪感を使う課金誘導、脆弱な層への課金オファーの個別化、確率の不透明化、退出を妨げる設計）は提案しない
- 最後に、ユーザーへ「次にやること」を3つ以内で示す（例: 会話NPCがあれば `/game-ai-character`）

## 5. ナレッジに戻す
企画で新しく分かったこと（例: 既存ゲームの続ける仕掛けの良い実装）があれば、ユーザーに「ナレッジに事例として追加するか」を最後に一言提案する。
