# ORBIT SWITCH に AI 機能を足す 企画書

> 前提: 既存のワンタップ・アクション（1プレイ数十秒）への機能追加。対象は全年齢（年齢区分は未設定）。プラットフォームは Web（PWA）と iOS。地域は日本語圏と英語圏。規模は個人開発＋AIコーディングアシスタント、予算はほぼゼロ（課金・広告なし）
> 対象コード: [kouki0727mickey/orbit-switch](https://github.com/kouki0727mickey/orbit-switch) のコミット `8002a6d`（読み取りのみ。企画時はこのリポジトリのブランチにあった）

## 一言で言うと
**AIはまず「作る側」に置き、プレイ中には置かない。** プレイ中の AI は、効果が見込める1機能だけを、後から試す。

- **フェーズ1（プレイ中の AI 呼び出しなし・運営費ゼロ）**
  - **A. 軌道パターン工房**: AI にトゲの配置パターンを大量に提案させ、既存の公平性ボットで合否を決める。通ったものだけを人が選んで入れる
  - **B. 上達の鏡**: 死因をコードで判定し、結果画面に「なぜ死んだか・何が上達したか」を一言で出す。文言は開発時に AI で下書きし、人が選んで端末内に持つ
- **フェーズ2（検証してから決める）**
  - **C. 言葉でステージ**: 「猫みたいに気まぐれな軌道」のような言葉を、AI がステージのパラメータに翻訳する。友だちと共有できるコードになる

💡 ORBIT SWITCH の強みは、手触りの良いコアループと「端末の外にデータを出さない」ことにある。プレイ中の AI は、この2つを崩さない範囲でしか足さない。

## コアループ（AIを外しても触って楽しいか）
- **今のコアループ**: タップでリングを切り替え → トゲをよける・ジェムを取る → 点数・コンボ・FEVER。1プレイ数十秒で、死んだらすぐリトライ（`README.md`）
- **AIを外しても楽しいか**: 楽しい。既に完成しているので、AI 機能はコアループの代わりにならない。役割は**飽きを遅らせること（A）**と**上達を見えるようにすること（B）**
- **今の弱点**: 配置パターンは4種類（1本トゲ、ジグザグ、ジェムの列、2連トゲ。`js/core.js` の `spawnBeat`）。上手な人ほど早く「見慣れた」状態になる。💡 飽きの原因はここだと考え、A で手を入れる

## AIの役割
| 機能 | AIがやること | ルールとして固定すること（コード側） | 根拠 |
|---|---|---|---|
| A. 軌道パターン工房（開発時） | パターン記述言語（DSL）で、新しいトゲ・ジェムの配置を提案する（例: 「3連ジグザグの後に、切り替えの誘惑になるジェムの列」）。名前と、なぜ面白いかの説明も付ける | DSL の文法チェック。**公平性ボット**（完璧ボットが100シードで90秒以上生き残る、人間ボットが序盤を95%以上生き残る、見えない壁がない）に通らないものは捨てる。難易度帯（`difficulty` の値）ごとの出現率はコードが決める | 原則2「ルールはコード、言葉はAI」、原則6「人が種と審美眼を担う」、`games.md`「PCG」 |
| B. 上達の鏡（開発時に下書き） | 「死因 × 腕前 × 調子」の組み合わせごとに、短い一言を日本語・英語で下書きする（例: 遅れ切り替え × 中級 × 自己ベスト更新直後 →「今日いちばんの伸び。切り替えがあと半拍早ければ、もっと先へ」） | **死因の判定はコード**（死んだ時のトゲの位置、最後の切り替えからの時間、パターンの種類）。どの一言を出すかもコードが選ぶ。文言は人が全部読み、選んでから入れる | P23「上達の鏡」、P16「事実はエンジンが持つ」、`engagement-design.md` グリーンパターン「上達の可視化」 |
| C. 言葉でステージ（プレイ中・フェーズ2） | プレイヤーの言葉を、決められた項目（速さ、トゲの密度、ジェムの量、パターンの重み、色）の値と、決められた語彙から選んだステージ名に翻訳する | 値の範囲と組み合わせは**コードが丸める**（公平性ボットに通る範囲だけ）。ステージ名は固定の語彙リストから番号で選ばせ、自由な文章は画面に出さない。共有コードはパラメータとシードだけ | P15「意図の構造化」、原則4「プレイヤーの入力が最大のコンテンツ」、原則1「不確実性を遊びにする」、P24「共有したくなる瞬間」 |

**AIでなければ成り立たないか**
- **A**: 人が1つずつ設計しても作れる。AI は量と意外な組み合わせで効く。公平かどうかは既存のボットで機械的に確かめられるので、この種のゲームで**一番相性がいい使い方**だと考える 💡
- **B**: 文言は人でも書ける（組み合わせは数十〜数百）。AI は日英の下書きの速度で効く。**プレイ中に生成する必要はない**ので、あらかじめ作っておく（原則7「コストを体験設計に含める」）
- **C**: スライダーでも同じパラメータは作れる。AI が効くのは、**言葉の解釈が予想外で面白い**ときだけ。これが成り立つかは分からないので、フェーズ2で検証する。スライダー版で足りるなら、スライダー版を選ぶ

**採らない案**
| 案 | 採らない理由 | 根拠 |
|---|---|---|
| 動的難易度調整（DDA） | 通常モードとデイリーチャレンジの点数は、同じ条件で比べられることに価値がある。こっそり難易度を変えると、ベスト・共有・デイリーの意味が崩れる | `games.md`「DDA」（気付かれないことが条件）、`engagement-design.md` 判定表「透明性」 |
| AI の相棒・実況キャラ | 1プレイ数十秒のゲームに会話は合わない。関係性を報酬にすると依存に寄りやすく、コンパニオン規制の論点も増える | P23 の課題、`games.md`「会話NPCとAIコンパニオン規制」 |
| 離脱予測・通知 | 今は通知も計測もない。ここに足すと「端末の外にデータを出さない」強みを失う | `engagement-design.md` 判定表「個別化の目的」、公開前チェック「問題なし」 |

## ハマる仕組み（動機とループ）
| ループ | 今 | 足すもの | 効く欲求 |
|---|---|---|---|
| コア（秒） | 切り替え・ニアミス・FEVER | A: 新しいパターンで、読み合いの種類が増える | 有能感（フロー） |
| メタ（分〜日） | ミッション、レベル、スキン、デイリー | B: 結果画面の「死因と上達」。死因ごとの成績を端末内で記録し、「遅れ切り替えのミスが先週より3割減った」と見せる | 有能感（上達の実感） |
| ソーシャル（日〜週） | 点数の共有 | C: 言葉で作ったステージを共有コードで送り合う。「このステージで何点取れる？」 | 関係性、自律性（自分で作る） |
| ライブ（週〜月） | なし | A: 通ったパターンを「今週の新しい軌道」として少しずつ足す（アップデートの配信で。サーバーは要らない） | 好奇心 |

- 💡 B の一言は「もう一回」を押させるためではなく、**次の1回で何を試すか**を渡すために使う。「今日はここまで」の一言もこの枠で出す（下の健全性の点検）
- A の新しいパターンは、デイリーチャレンジにも入れる。誰もが同じ日に同じ新パターンに出会うので、共通の話題になる（`ai-native-entertainment.md` 💡「共通の骨格＋個別の肉付け」）

## 健全性の自己点検
| 問い | 答え |
|---|---|
| やめた後にどう感じるか | B が「何が上達したか」を渡すので、負けても得たものがある形で終われる 💡（プレイテストで確認する） |
| 動機の源 | 上達したい（A・B）、作って見せたい（C）。「失いたくない」に当たるのは既存の連続ログインのボーナスだけ。これは公開前チェックの改善提案1（1日空いても切れない猶予、または累計日数）を**この企画で一緒に直す** |
| 個別化の目的 | B は死因と腕前に合わせた言葉。体験の質のためで、滞在時間の最大化ではない |
| 個別化の対象 | ゲームプレイだけ。課金がないので価格の個別化はない |
| 透明性 | A は「AI が提案し、ボットで公平性を確かめ、人が選んだ」と説明できる。B は死因の判定方法を画面で説明できる。C は「言葉を AI がステージの設定に翻訳します」と明示する（P30） |
| 終わり方 | 公開前チェックの改善提案2を B で実装する。連続30分を超えたら、B の枠に「今日のベスト ○点。ここで区切ると、明日の1回目が一番冴えます」を出す（P22 の考え方をキャラなしで使う） |

- **レッドライン**: 当たる要素はない。課金・ガチャ・AIキャラがなく、B の一言は「罪悪感」「取り残される」を使わない。文言の選定基準に「もう一回を煽る言葉、休むことを否定する言葉を入れない」を加える（`engagement-design.md` レッドライン、P31 の考え方）
- **未成年への配慮**: A・B はプレイ中に AI を使わないので、今と同じ。C は自由入力を AI に送るので、年齢区分とあわせて、送った言葉の扱い（下のプライバシー）を決めてから出す

## コストとモデル選び
料金は `claude-haiku-4-5` を入力 $1 / 出力 $5（100万トークンあたり）として見積もった（`prototype/npc_lab/llm.py` の料金表。実行前に最新の料金を確認する）。

| 機能 | いつ呼ぶか | 回数と費用の見積もり | 上限と上限到達時の挙動 |
|---|---|---|---|
| A. 軌道パターン工房 | 開発時だけ | 1回の提案で入力 約2,000・出力 約600トークン → 約 $0.005。200案で 約 $1 | `--dry-run` で見積もり、`--max-usd 1.00` を付ける。上限に達したら止まり、生成済みの案は残る。**運営費はゼロ** |
| B. 上達の鏡 | 開発時だけ | 300の一言 × 日英を20回に分けて下書き（1回で入力 約1,500・出力 約1,500トークン）→ 約 $0.20 | 同上。**運営費はゼロ**。端末内の表から選ぶだけなので、オフラインでも動く |
| C. 言葉でステージ | プレイ中（フェーズ2） | 1回で入力 約800（うち固定の指示はキャッシュ）・出力 約150トークン → 約 $0.0016。1人1日3回まで → 最大 約 $0.005／人・日。1日の利用者1,000人のうち3割が使うと 約 $1.4／日、月 約 $45 | **1人1日3回（P37）と、サーバー全体の1日の上限（例: $3）**。上限に達したら「今日の言葉の枠は終わり。スライダーで作れます」と出し、同じパラメータを手で作れる画面に切り替える。遊べなくなることはない |

- **モデル選び**: A・B・C すべて `claude-haiku-4-5` から始める。A でボットの合格率が低すぎるときだけ、大きなモデルを比べる（P34、`STRATEGY.md`「API試験の費用方針」）
- **C の構成**: API キーは端末に置けないので、中継サーバーが要る。💡 収益がないので、C の運営費は開発者の持ち出しになる。月 $45 を払い続けられるかが、C を出すかどうかの判断材料の1つ
- **iOS 版**: ゲームの中身は `js/core.js` と `ios/.../GameCore.swift` の2か所にある。A のパターンを DSL のデータ（JSON）として持ち、両方が同じデータを読む形にすると、二重の実装を避けられる 💡

## リスクと検証計画
| # | 危ない仮説 | 最小コストでの確かめ方 | 費用 |
|---|---|---|---|
| 1 | **（一番危ない）AI の提案したパターンは、公平で、かつ今の4種類より面白い** | まず DSL を作り、今の4種類を DSL で書き直して、ボットの結果が変わらないことを確かめる（API なし）。次に Haiku で20案を出し、ボットの合格率を見る。通った案から人が5つ選び、プレイテストで今の4種類と混ぜて遊んでもらう | API は 約 $0.10（`--max-usd 0.50`）。残りはコードとプレイテスト |
| 2 | 死因を、プレイヤーが納得する精度で判定できる | API なし。`tests/bot.js` の人間ボットをわざとミスさせ、判定器が正しい死因を返すかをテストする。今の `death` イベントには原因の情報がないので、ぶつかったトゲとパターンの種類、最後の切り替えからの時間を足す | $0 |
| 3 | B の一言は「次に試すこと」を渡し、煽りにならない | 下書きの前に、選定基準（煽らない、休むことを否定しない、20字前後）を決める。プレイテストで「次に何を試すか分かったか」「押し付けがましくないか」を聞く | 約 $0.20 |
| 4 | C の「言葉の解釈」は、スライダーより面白い | **API なしで先に作る**: パラメータの空間とスライダー版を作り、公平性ボットで範囲を確かめる。次に、用意した言葉50個を Haiku に翻訳させ（約 $0.08）、結果を人が見て「予想外で面白い」割合を数える。プレイテストで、スライダー版と言葉版を両方遊んでもらう。**スライダー版で十分なら C は出さない** | 約 $0.08＋サーバーは作らない |

実行する順番: 2 → 1 → 3 → 4（2と3は API がほぼ要らず、1が一番の山場）。

## 分かっていないこと
- 飽きの原因は、本当にパターンの種類の少なさか。スピードの上限や、スキン以外の目標の少なさかもしれない（プレイテストで聞く）
- A の生成物（レベルのデータ）が、Steam や App Store の「AI 生成コンテンツ」の申告対象に入るか `【要確認】`
- C の運営費を、課金も広告もないまま続けられるか。端末内の小型モデル（P35）で置き換えられるか
- 結果画面の一言に、何種類あれば「またこれか」と感じないか 💡 死因6種 × 腕前3段 × 調子3種で約50通り、各3案で150程度と見込む
