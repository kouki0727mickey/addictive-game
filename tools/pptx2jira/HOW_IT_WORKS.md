## 1. 全体: 何が入って何が出るか

| 段階 | スクリプト | 入力 | 出力（作業ディレクトリ `W` の中） | 外部とのやりとり |
|---|---|---|---|---|
| ① 抽出 | `extract.py` | `資料.pptx` | `slides.json`、`extracted.md`、`images/`、`renders/` | LibreOffice（ローカル） |
| ② Markdown 化 | `vlm_markdown.py` | `slides.json`、`images/`、`renders/` | `md/slide-NNN.md`、`deck.md`、`vlm_report.json`、`.cache/vlm/` | vLLM |
| ③ 課題の計画 | Claude Code 自身、または `plan_issues.py` | `deck.md`、`prompts/plan_issues.md` | `issues.json` | （`plan_issues.py` のときだけ）Claude API |
| 検査 | `issues_schema.py` | `issues.json`、`deck.md` | 画面への結果（`--fix` なら `issues.json` を上書き） | なし |
| ④ 登録 | `jira_push.py` | `issues.json`、`deck.md`、（任意）`renders/` | `jira_state.json`、画面への結果 | Jira |

**段階の間は必ずファイルで受け渡す。** どの段階も、前の段階のファイルさえあれば単独でやり直せる。手で直したファイルを次の段階に渡すこともできる。

## 2. 段階① 抽出（extract.py）

### 処理の順番

```
main()
 ├─ extract(pptx)                       … スライドを 1 枚ずつ読む
 │   ├─ walk_shapes()                   … 図形を再帰的にたどり、ブロックの一覧にする
 │   ├─ タイトルを決める
 │   ├─ xy_cut()                        … ブロックを読む順に並べ替える
 │   └─ notes_text()                    … 発表者ノート
 │   （全スライドの後）ロゴの判定、text_units（網羅率の単位）を作る
 ├─ 前回と別の資料なら、古い md/ renders/ deck.md vlm_report.json を消す
 ├─ render_slides()                     … LibreOffice でスライド画像を作る
 └─ slides.json と extracted.md を書く
```

### ステップ 1: 図形をたどってブロックにする（walk_shapes）

スライド上の図形を 1 つずつ見て、種類ごとに「ブロック」という辞書にする。

| 図形の種類 | 判定のしかた | ブロックの中身 |
|---|---|---|
| グループ | `shape_type == GROUP` | ブロックにはしない。中の図形に対して、座標の変換を重ねて再帰する |
| スライド番号・日付・フッター | プレースホルダの種類 | 捨てる |
| 表 | `has_table` | `rows`（2 次元の文字列）、`header`、`merged` |
| グラフ | `has_chart` | `chart_type`、`title`、`categories`、`series`（名前と値） |
| SmartArt | 中に `graphicData uri=".../diagram"` がある | `items`（文字と階層） |
| 画像 | `Picture` のインスタンス（画像のプレースホルダも含む） | 画像ファイル、代替テキスト、装飾かどうか |
| 埋め込み（Excel など） | OLE | `prog_id` だけ。中身は取らない |
| それ以外で文字があるもの | テキストフレームがある | `paragraphs`（段落の一覧） |

すべてのブロックに、スライドに対する比（0〜1）の外接矩形 `bbox = [x, y, 幅, 高さ]` を付ける。

**例: スライド 4 の結果（slides.json から抜粋）**

```json
{"kind": "table", "bbox": [0.0375, 0.2, 0.6, 0.4],
 "rows": [["フェーズ","期間","担当"], ["設計","10月","決済チーム"], ["実装","11月〜12月","決済チーム"], ["移行","1月","インフラ"]],
 "merged": [[1, 2, 2, 1]]}
{"kind": "text", "bbox": [0.0375, 0.6667, 0.15, 0.0667], "paragraphs": [{"text": "PM: 山田", "md": "PM: 山田", "level": 0, "bullet": null}]}
{"kind": "text", "bbox": [0.0375, 0.7467, 0.15, 0.0667], "paragraphs": [{"text": "開発: 決済チーム", ...}]}
```

#### 段落の読み方

段落ごとに次の 4 つを取る。

- `text`: 飾りなしの文字（網羅率の計算や検査に使う）
- `md`: Markdown の文字。太字のランは `**…**`、斜体は `*…*`、ハイパーリンクは `[…](URL)`、改行は `<br>`
- `level`: 段落 XML の `lvl`（0 が一番上）
- `bullet`: 行頭の記号。段落の設定で決まる
  - `buNone` → なし
  - `buAutoNum` → 番号。階層ごとに数える。親の番号が進んだら子は 1 から。番号の並びが途切れたら振り直す
  - `buChar` → `-`
  - 指定がないとき → 本文プレースホルダか、`level` が 1 以上なら `-`

行頭が `#` や `1.` などで始まる普通の文は、Markdown の見出しやリストに化けないよう `\#` のようにエスケープする。

**例: スライド 2 の段落**

| text | md | level | bullet |
|---|---|---|---|
| ユーザー認証をSSOに統一する | （同じ） | 0 | `-` |
| 対象: 社内管理画面と加盟店ポータル | （同じ） | 1 | `-` |
| 決済APIのレスポンスを300ms以内にする | `**決済APIのレスポンスを300ms以内にする**` | 0 | `-` |
| 仕様書 を参照 | `[仕様書](https://example.com/spec) を参照` | 1 | `-` |
| 監査ログを7年保管する | （同じ） | 0 | `1.` |
| 障害時は5分以内に切り替える | （同じ） | 0 | `2.` |

#### 表の結合セル

python-pptx では、結合範囲の起点のセルが値を持ち、残りのセルは「結合された側」（`is_spanned`）になる。
起点の値を結合範囲のすべてのセルに書き込み、範囲は `merged` に `[行, 列, 縦の数, 横の数]` で残す。
例では「担当」列の 2〜3 行目が結合されている。そのため「実装」の行の担当も「決済チーム」になる。起点だけに値を入れると、Claude が行ごとに読んだとき、実装の担当が空に見えてしまう。

#### グループ図形の座標

グループの中の図形は、グループ独自の座標系（`chOff`・`chExt`）で位置を持つ。スライド上の位置は次の式で求める。

```
倍率 = グループの大きさ(ext) ÷ 子の座標系の大きさ(chExt)
スライド上の x = グループの位置(off.x) + (子の x − chOff.x) × 倍率
```

グループが入れ子なら、この変換を外側から順に掛け合わせる。
例では、子の座標系が 4in×2.2in で、スライドには 2in×1.1in（半分）で置かれている。2 つ目の箱（子の座標で y=1.2in）は、スライド上では 5.0 + 1.2 × 0.5 = 5.6in（比で 0.7467）に来る。

#### SmartArt

SmartArt は見た目の図形とは別に、データ部（`dgm:dataModel`）に「点」（項目）と「接続」（親子関係）を持っている。
文書の根の点から、`parOf`（親子）の接続を `srcOrd`（並び順）の順にたどる。深さを階層として `{"text", "level"}` の一覧にする。
接続からたどれなかった点も、落とさずに最後に足す。

#### 画像

- 中身のハッシュ（SHA-1 の先頭 16 桁）をファイル名にして `images/` に保存する。同じ画像が何度出ても 1 つにまとまる
- 次のどれかに当たれば装飾（`decorative: true`）とする:
  - スライド面積の 0.4% 未満
  - 縦か横が 40px 未満
  - スライドが 3 枚以上あり、同じ画像が半数以上のスライドに出る（ロゴ）
- 代替テキスト（`descr`）を取る。ただし `image.png` のようなファイル名だけのもの（ツールが自動で入れたもの）は捨てる
- 装飾の画像は VLM に送らず、Markdown にも出さない

例では、右上のロゴ（面積 0.33%、5/6 枚に出る）は装飾になる。スライド 5 の構成図（面積 18.7%、代替テキスト「新しいシステム構成図」）は内容の画像になる。

### ステップ 2: タイトルを決める

1. タイトルのプレースホルダの文字を使う
2. それがなければ、上から 20% 以内にある、1 段落・60 字以下の文字の箱のうち、一番上（同じ高さなら左）のものを題とみなす。`title_guessed: true` を付け、その箱は本文から外す

### ステップ 3: 読む順序を決める（xy_cut）

図形の並び順は、作った順か重なりの順で、読む順ではない。そこで、外接矩形の位置から順序を決める（再帰 XY-cut）。

1. 全ブロックの矩形を y 軸に投影し、どのブロックにも覆われていない帯（すき間）のうち、最も広いものを探す。x 軸でも同じことをする
2. 座標はスライドに対する比なので、16:9 のスライドでは x のすき間を縦横比（1.78）倍して、実際の長さにそろえる
3. y と x のうち、すき間の広い方で 2 つに切る（同じ広さなら上下で切る）。各ブロックは中心がどちら側にあるかで振り分ける。0.5% までの重なりは、すき間とみなす
4. 切った両側に、同じ処理を繰り返す
5. どこにもすき間がなければ、(上端, 左端) の順に並べる

**例: スライド 3（タイトルは本文から外してある）**

| ブロック | bbox [x, y, 幅, 高さ] |
|---|---|
| ロゴ | [0.900, 0.013, 0.075, 0.044] |
| 現状（見出し） | [0.0375, 0.213, 0.45, 0.08] |
| 決済処理が夜間バッチで遅い（＋詳細メモ） | [0.0375, 0.320, 0.45, 0.267] |
| 課題（見出し） | [0.525, 0.213, 0.45, 0.08] |
| リアルタイム化が必要（＋詳細メモ） | [0.525, 0.320, 0.45, 0.267] |

- 1 回目: y のすき間はロゴの下端 0.057 と見出しの上端 0.213 の間で 0.156。x のすき間は列の間 0.4875〜0.525 で、0.0375 × 1.78 = 0.067。y の方が広いので上下で切る → [ロゴ] と [残り 4 つ]
- 2 回目（残り 4 つ）: y のすき間は見出しと本文の間で 0.320 − 0.293 = 0.027。x のすき間は 0.067。x の方が広いので左右で切る → [左の列] と [右の列]
- 3 回目（各列）: 上下で切る → 見出し、本文

結果は「現状（見出し）→ 夜間バッチ… → 課題（見出し）→ リアルタイム化…」。もし常に上下から切っていたら、「現状（見出し）→ 課題（見出し）→ 夜間バッチ… → リアルタイム化…」と左右を交互に読んでしまう。

### ステップ 4: ノートと text_units

- 発表者ノートは、ノートのテキストフレームの文字をそのまま取る
- `text_units` は「このスライドの文字の一覧」で、段階②の網羅率の分母になる。タイトル、全段落、表の全セル、グラフの題・分類名・系列名、SmartArt の項目を入れる

例（スライド 2）: `["機能要件", "ユーザー認証をSSOに統一する", "対象: 社内管理画面と加盟店ポータル", "決済APIのレスポンスを300ms以内にする", "仕様書 を参照", "監査ログを7年保管する", "障害時は5分以内に切り替える"]`

### ステップ 5: スライド画像を作る（render_slides）

1. pptx を一時ディレクトリにコピーする。LibreOffice を `--headless` で起動し、PDF に変換する。そのとき非表示スライドも出力する設定（`ExportHiddenSlides`）にして、PDF の n ページ目がスライド n になるようにする。LibreOffice の設定ディレクトリも一時ディレクトリに作り、他の LibreOffice と干渉しないようにする
2. `pdftoppm -r 110 -png` で各ページを PNG にする
3. ページ数とスライド数を比べる
   - 同じ → `renders/slide-NNN.png` として割り当てる
   - 表示スライドの数と同じ → 表示スライドだけに割り当て、警告を出す
   - どちらでもない → 画像は使わず、警告を出す（ずれた画像を VLM に見せるより安全）
4. LibreOffice や pdftoppm がない、または失敗したときは、警告を出して先に進む。段階②は文字だけで動く

### ステップ 6: extracted.md を書く

ブロックを決まった規則で Markdown にする（VLM を使わない、毎回同じ結果になる変換）。

| ブロック | Markdown |
|---|---|
| 段落 | `bullet` があれば `字下げ(2 文字×level) + 記号 + md`。なければ段落。箇条書きの直後の普通の段落の前には空行を入れる（リストの続きとして読まれないように） |
| 表 | Markdown の表。セル内の改行は `<br>`、`\|` はエスケープ |
| グラフ | `**グラフ（種類）: 題**` と、系列 × 分類の表。題がなく系列が 1 つなら、系列名を題にする |
| SmartArt | 階層つきの箇条書き |
| 画像（装飾以外） | `![代替テキスト](images/…)` |
| 埋め込み | `> 埋め込みオブジェクト（…）。中身は抽出していない` |

スライドごとに、次の形で出力する。

```markdown
<!-- slide: 2 -->

## スライド 2: 機能要件

*セクション: …*（セクションがあれば）

（本文）

### 発表者ノート

> SSOはOktaを想定。担当は認証チーム。期限は11月末。
```

ファイルの先頭には `# ファイル名` と `<!-- source-sha256: … -->`（pptx のハッシュ）を書く。このハッシュは、段階④で「どの資料から作った課題か」を表すラベルにも使う。非表示スライドは、`--include-hidden` を付けない限り出力しない。

## 3. 段階② Markdown 化（vlm_markdown.py）

### 処理の順番

```
main()
 ├─ 対象のスライドを選ぶ（非表示を除く、--only で絞る）
 ├─ スライドごとに process_slide() を並列に実行（既定 4 本）
 │    ├─ build_messages()    … VLM への入力を組み立てる
 │    ├─ 画像がなければ抽出結果をそのまま返す（text_only）
 │    ├─ キャッシュがあれば返す
 │    ├─ VLM を呼ぶ → 後処理 → 検査
 │    ├─ 不合格ならやり直し（既定 1 回）→ 後処理 → 検査
 │    └─ 採用するものを決める（合格したもの／だめなら fallback）
 │    ※ 例外が出たスライドは抽出結果で埋める（error_fallback）
 ├─ md/slide-NNN.md を書く
 ├─ deck.md を組み立てる（write_deck）
 └─ vlm_report.json を更新する
```

### ステップ 1: VLM への入力（build_messages）

OpenAI 互換の `/v1/chat/completions` に、次のメッセージを送る。

- **system**: 指示（ソースの `SYSTEM_PROMPT`）。要点は次のとおり
  1. 原文の文字は一字一句そのまま使う（要約・言い換え・翻訳・省略をしない）
  2. スライド画像を見て、人が読む順序とまとまりで並べる
  3. 表とグラフは中身を書かず、`{{TABLE-1}}` のような行を置くだけにする
  4. 矢印などの流れは「A → B」で書く
  5. 埋め込み画像は `> 図（IMG-n）: ` で 1 枚ずつ説明する
  6. 読めない文字は【要確認】にする
  7. 原文にも画像にもないことを書かない
  8. 本文だけを出す（タイトルの見出しやコードフェンスを付けない）
- **user**: 次の順に並べる
  1. `原文（JSON）:` と、座標などを除いた原文。表とグラフには `TABLE-1`・`CHART-1` の id を、内容の画像には `IMG-1` の名前を付ける
  2. `スライド全体の画像:` と、`renders/slide-NNN.png`（長辺 1600px に縮小した PNG の data URL）
  3. `IMG-1:` と、その画像。内容の画像を面積の大きい順に、最大 `--max-images`（既定 3）枚。EMF・WMF など開けない形式は送らず、注意書きに残す
  4. `このスライドの本文を Markdown にしてください。`
- **パラメータ**: `temperature: 0`、`max_tokens: 4096`、`--extra-body` で渡した追加の値

**例: スライド 5 の user メッセージ（画像は省略）**

```
原文（JSON）:
{"title": "障害件数の推移", "blocks": [
  {"type": "chart", "id": "CHART-1", "chart_type": "COLUMN_CLUSTERED", "title": null,
   "categories": ["4月","5月","6月"], "series": [{"name": "障害件数", "values": [12.0, 8.0, 3.0]}]},
  {"type": "image", "name": "IMG-1", "alt": "新しいシステム構成図"}]}
スライド全体の画像: [PNG]
IMG-1: [PNG]
このスライドの本文を Markdown にしてください。
```

ロゴは装飾なので入らない。送らなかった画像がある場合（上限を超えた、形式が開けない）は、その旨を `vlm_report.json` の `notes` に残す。

### ステップ 2: 画像がないスライドは VLM を呼ばない

送る画像が 1 枚もない（スライド画像も内容の画像もない）なら、VLM に見せられる情報は原文と同じしかない。その場合は抽出結果の Markdown をそのまま使う（`status: text_only`）。速く、費用もかからず、文字も正確。

### ステップ 3: VLM を呼ぶ（VLMClient.chat）

- 200 が返ったら `choices[0].message.content` を使う。`finish_reason` が `length`（出力が途中で切れた）なら、エラーにする
- 408・429・5xx・接続エラーなら、2 秒、4 秒、8 秒、16 秒と待って、最大 5 回まで呼ぶ
- それ以外の 4xx はすぐにエラーにする（モデル名の誤りなど、待っても直らないため）

### ステップ 4: 後処理（clean_output → fill_slots）

1. `<think>…</think>`（考える過程を出すモデルの出力）を消す
2. 全体が ```` ```markdown … ``` ```` で囲まれていたら外す
3. 先頭の行がタイトルの見出しなら消す（見出しはこちらで付ける）
4. `#`・`##` の見出しを `###` に下げる（スライドの見出し `##` より上の階層にしない）
5. `{{TABLE-n}}` と `{{CHART-n}}` の行を、抽出した表とグラフの Markdown に差し替える
   - 同じ id の 2 回目と、存在しない id の行は消す
   - VLM が置き忘れた表・グラフは、末尾に足す（落とさない）

### ステップ 5: 検査（evaluate）

次の 3 つをすべて満たせば合格（`ok: true`）。

| 検査 | 内容 | 結果の項目 |
|---|---|---|
| 網羅率 | 本文の `text_units`（タイトルを除く）が出力に残っている割合 ≥ `--min-coverage`（既定 0.95） | `coverage`、`missing`（落ちた行） |
| 作られた数字 | `> ` で始まる行（図の説明）を除いた本文に、原文にない 2 桁以上の数字がない | `invented_numbers` |
| 図の説明 | 送った画像ごとに `> 図（IMG-n）: ` の行がある | `missing_figures` |

網羅率と数字の検査の中身は[次の章](#4-網羅率と数字の検査のしくみcommonpy)。図の説明の中を数字の検査から外しているのは、画像の中の文字（例: 構成図の中の「Gateway」やポート番号）は原文にないのが普通だから。

### ステップ 6: やり直し

不合格なら、会話を続ける形で、もう一度呼ぶ（既定 1 回、`--quality-retries` で変更できる）。

```
[system] …指示…
[user]   …原文と画像…
[assistant] （1回目の出力）
[user]   前の出力には次の問題があります。原文の文字をそのまま使い、直した本文の Markdown 全体を出し直してください。
         原文の次の行が含まれていません。すべて含めてください:
         - 仕様書 を参照
         - 監査ログを7年保管する
         - 障害時は5分以内に切り替える
```

これは実際に記録したもの（偽の VLM に、1 回目だけ後半の行を落とさせた）。作られた数字や説明のない画像があれば、それも同じ形で列挙する。
この例では、網羅率が 1 回目 0.6353 → 2 回目 1.0 になり、2 回目を採用した（`status: vlm_retry`）。

### ステップ 7: どれを採用するか

- 合格した試行があれば、その中で網羅率の最も高いものを採用する（`vlm`、または `vlm_retry`）
- どの試行も不合格なら、**抽出結果の Markdown**に、試行の中で最も長い図の説明（`> 図` で始まる引用ブロック）を付け足したものを使う（`fallback`）。文字を落としたり数字を作ったりした出力は、本文には使わない
- 呼び出しが例外で失敗したら（vLLM が落ちている、など）、そのスライドは抽出結果を使う（`error_fallback`）。他のスライドは続ける

### ステップ 8: キャッシュ

結果は `.cache/vlm/<キー>.json` に保存する。キーは、指示の版（`PROMPT_VERSION`）・モデル名・送ったメッセージ全体（画像を含む）・合格の閾値のハッシュ。同じ入力なら 2 回目は VLM を呼ばない。指示を変えたら `PROMPT_VERSION` を上げるので、古い結果は使われない。`--no-cache` で無視できる。

### ステップ 9: deck.md を組み立てる（write_deck）

- 各スライドの本文は `md/slide-NNN.md` から取る。なければ抽出結果を使う（`--only` で一部だけ処理したとき）
- そこに、スライドの区切りのコメント・見出し・セクション・**原文のままのノート**を付けて、1 つのファイルにする。ノートを VLM に通さないのは、担当・期限などの言い換えを防ぐため
- `--rebuild-deck` は VLM を呼ばずにこの組み立てだけをする。`md/slide-NNN.md` を手で直したときに使う

`vlm_report.json` には、スライドごとに `status`・`coverage`・`missing`・`invented_numbers`・`missing_figures`・試行の回数と網羅率・秒数・トークン数を記録する。

## 4. 網羅率と数字の検査のしくみ（common.py）

### 正規化（normalize）

比較の前に、生成文と原文の両方を同じ規則でならす。

1. `<!-- … -->`、画像（`![…](パス)` → 代替テキストだけ残す）、リンク（`[文字](URL)` → 文字だけ残す）を除く
2. NFKC で全角・半角をそろえ、小文字にする
3. `<br>` を空白にする
4. Markdown の記号と行頭記号（`* _ ` # > | ~ [ ] ( ) - + • ● ・ ※` など）を空白にする
5. 空白をすべて消す

例: `- **決済API**のレスポンスを３００ms以内に [仕様](http://x/1)` → `決済apiのレスポンスを300ms以内に仕様`

### 網羅率（coverage）

```
for 原文の単位 u in text_units（正規化して重複を除く）:
    分母 += len(u)
    if u が生成文に含まれる: 分子 += len(u)
網羅率 = 分子 / 分母
```

- 重みは文字数。長い行を落とすほど大きく下がる
- 「含まれる」の判定:
  - 完全に部分文字列として含まれれば OK
  - 6 字未満の短い単位（「Q3」など）は、完全一致だけを認める。あいまいに一致させると「Q3」が「Q4」に一致してしまうため
  - 6 字以上なら、あいまい一致。生成文の中で、原文と同じ長さ前後の窓を、一致しそうな位置（`SequenceMatcher` の一致ブロックから求める）の前後に置き、類似度（`ratio`）が 0.85 以上の窓があれば OK。VLM が句読点を変えた、空白を入れた程度の差は許す

例: 原文が「監査ログを7年保管する」「障害時は5分以内に切り替える」で、生成文が「監査ログを7年保管する」だけなら、網羅率は 11 ÷ (11 + 14) = 0.44、落ちた行は「障害時は5分以内に切り替える」。

### 作られた数字（invented_numbers）

1. 生成文から、コメント・画像のパス・リンク先を除く（ファイル名のハッシュの数字を拾わないため）
2. 原文と生成文から数字を取り出す（`1,000` や `3.5` も 1 つの数字として扱う）。カンマは除き、`12.0` は `12` とみなす（グラフの値と本文を突き合わせるため）
3. 生成文にあって原文にない数字のうち、2 桁以上のものを返す。1 桁の数字は見出しや箇条書きの番号として VLM が付けることが多いので、対象外にする

原文の側には `text_units` と、VLM に送った原文の JSON（グラフの値を含む）を使う。

## 5. 段階③ 課題の計画（Claude）

### 2 つの経路と共通の指示

| 経路 | いつ使うか | 何が動くか |
|---|---|---|
| Claude Code 自身（スキルの既定） | 対話で 1 つの資料を扱うとき | スキルの手順に従い、Claude Code が `prompts/plan_issues.md` と `deck.md` を読んで `issues.json` を書き、自分で見直す。API の費用はかからない |
| `plan_issues.py` | 大量の資料をまとめて流すとき、CI | Claude API を呼ぶ |

どちらも同じ指示（`prompts/plan_issues.md`）と同じスキーマ（`issues_schema.PLAN_SCHEMA`）を使う。

### 指示（prompts/plan_issues.md）が求めること

- **切り方**: エピック（大きなテーマ、目安 1〜6 個）→ 課題（完了条件が 1 つの作業。story / task / bug）→ サブタスク（資料が手順や内訳を明示しているときだけ）。同じ内容が複数のスライドに出たら 1 つにまとめる
- **根拠**: 課題ごとに、資料の文を一字一句そのまま 1〜3 個、`evidence` に引用する
- **推測の申告**: 期限・優先度・担当は、資料に書かれているときだけ入れる。年や日を補ったら `inferred_fields` に書く。担当は資料の表記のまま書き、人を推測しない
- **課題にしないもの**: 表紙・目次・背景だけのスライドは、理由と一緒に `skipped_slides` に入れる。曖昧な点や矛盾は `open_questions` に入れる

### issues.json の形

```json
{
  "version": 1,
  "source": {"file": "sample.pptx", "sha256": "3588d9…"},
  "project_key": "PAY",
  "plan": {
    "epics": [
      {"ref": "E1", "summary": "新決済基盤の機能要件を満たす", "description": "…", "labels": ["payments"], "source_slides": [2],
       "issues": [
         {"ref": "E1-1", "type": "story", "summary": "ユーザー認証をSSOに統一する",
          "description": "社内管理画面と加盟店ポータルの認証を SSO に統一する。",
          "acceptance_criteria": ["社内管理画面と加盟店ポータルの両方で SSO ログインできる"],
          "priority": "", "due_date": "2026-11-30", "assignee_hint": "認証チーム",
          "labels": ["auth", "sso"], "source_slides": [2],
          "evidence": ["ユーザー認証をSSOに統一する", "期限は11月末"],
          "depends_on": [], "inferred_fields": ["due_date"], "subtasks": []}
       ]}
    ],
    "unassigned_issues": [],
    "open_questions": [{"question": "SSO の期限「11月末」は 2026年11月で正しいか", "source_slides": [2]}],
    "skipped_slides": [{"slide": 1, "reason": "表紙"}],
    "review_notes": []
  }
}
```

`due_date` の「2026-11-30」は、資料の「11月末」に年を補ったもの。そのため `inferred_fields` に `due_date` が入っている。

スキーマは Claude の構造化出力にそのまま渡せる形にしてある。null を使わず空文字や空の配列で表し、すべての object で全項目を必須、余分な項目は禁止にしている。

### plan_issues.py の動き

1. `deck.md` を読み、リクエストを組み立てる（request_kwargs）
   - `system`: 指示。`cache_control` を付けてキャッシュする
   - `messages`: user の 1 件目のブロックに `<deck>…</deck>`（ここにも `cache_control`）、2 件目のブロックに依頼文
   - `output_config.format`: `{"type": "json_schema", "schema": PLAN_SCHEMA}`
   - `output_config.effort`: `--effort`（既定 `high`）。`claude-haiku-4-5` は effort を受け付けないので付けない
   - `claude-opus-5-5` などの対応モデルでは、拒否されたときに別モデルで続ける `fallbacks: "default"`（ベータの `server-side-fallback-2026-07-01`）
2. 費用を見積もる
   - 入力トークン数は `count_tokens` で数える。数えられないとき（キーがない、など）は、文字数を 1 字 1 トークンとして多めに見積もる
   - 出力は「入力の半分、最低 4,000、上限 `max_tokens`」と仮定する
   - 見積もり = (入力 × 入力単価 + 出力 × 出力単価) × 呼び出し回数（`--review-pass` なら 2）
   - `--dry-run` なら、ここで見積もりを出して終わる。見積もりが `--max-usd`（既定 1 ドル）を超えたら、呼ばずに止まる
3. ストリーミングで呼び、最後のメッセージを受け取る
   - `stop_reason` が `refusal` か `max_tokens` なら止まる
   - 400・認証・レート制限・接続の各エラーは、それぞれ原因を書いて止まる
4. `--review-pass` なら、1 回目の課題案を JSON のまま依頼文に付け、「資料と突き合わせて直した版を同じスキーマで出す。直した点は `review_notes` に書く」と頼む。資料のブロックは 1 回目と同じなので、キャッシュから読まれて安くなる
5. 実際の使用量（キャッシュの読み込みは入力単価の 10%）から、かかった費用を計算する
6. 自動の直し（autofix）と検査（lint）をして、`issues.json` を書く。検査でエラーがあれば終了コード 1

## 6. 検査（issues_schema.py）

`lint(plan, deck_md)` は、`deck.md` を `<!-- slide: N -->` で区切ってスライドごとの文字にし、課題案と突き合わせる。

### エラー（登録を止める）

| 検査 | どう確かめるか |
|---|---|
| スキーマ | `jsonschema` で PLAN_SCHEMA に合うか。違反があれば、他の検査はしない |
| ref の重複 | エピック・課題・サブタスクの ref をすべて集めて数える |
| 根拠の引用 | 引用ごとに、まず**出典のスライド**の中を網羅率の判定（閾値 0.85）で探す。なければ資料全体を探し、別のスライドにあれば警告、どこにもなければ「作り話の疑い」としてエラー |
| 出典 | `source_slides` の番号が `deck.md` にあるか。エピック以外は 1 つ以上必要 |
| 依存 | `depends_on` の ref が存在するか、自分自身でないか。依存のグラフに循環がないか（深さ優先探索で、探索中の節点にもう一度来たら循環） |
| 要約 | 空でない、255 字以下（Jira の上限）、改行がない |
| ラベル | 空白や記号がない（Jira が拒否する） |
| 期限 | `YYYY-MM-DD` として読めるか |

### 警告（人が判断する）

| 検査 | どう確かめるか |
|---|---|
| 数字の書き換え | 要約と受け入れ条件の数字（2 桁以上）が、出典のスライドにあるか。「300ms」を「200ms」にしたものなどを拾う |
| 期限の根拠 | `inferred_fields` に `due_date` がない期限の、月か日の数字が、引用か出典のスライドにあるか |
| 担当の根拠 | `assignee_hint` が、出典のスライドに（正規化して）含まれるか |
| 重複 | 課題の要約どうしの類似度が 0.9 を超えないか |
| 取りこぼし | どの課題・問いにも使われておらず、除外の理由もないスライドがないか |
| その他 | 要約が 100 字を超える、課題のないエピック |

### 自動の直し（--fix）

意味を変えない直しだけをする。ラベルの空白や記号を `-` に置き換える（`sso login` → `sso-login`）、重複したラベルを除く、要約の改行や連続した空白を 1 つの空白にする。

## 7. 段階④ Jira 登録（jira_push.py・md_convert.py）

### 処理の順番

```
main()
 ├─ issues.json を読み、自動の直しをする
 ├─ deck.md があれば検査し、エラーがあれば止める（--allow-lint-errors で無視）
 ├─ 作る操作の一覧を作る（plan_operations）
 ├─ --offline なら一覧を出して終わる
 ├─ 事前確認（preflight）
 ├─ 状態ファイルを読む。ないものは Jira を検索して拾い直す（recover_state）
 ├─ 操作を順に実行する（--apply がなければ、何を作るかを出すだけ）
 └─ 結果を出す（作った課題、飛ばしたもの、エラー、警告、URL）
```

### 実際の通信の順番（Cloud、10 件を作った記録）

```
GET  /rest/api/2/serverInfo                       … 版の判定（Cloud なら以降 v3）
GET  /rest/api/3/myself                           … 認証の確認
GET  /rest/api/3/project/PAY                      … プロジェクトと課題タイプの一覧
GET  /rest/api/3/issue/createmeta/PAY/issuetypes/{id}  … タイプごとの作成画面の項目（4 回）
GET  /rest/api/3/issueLinkType                    … Blocks のリンクがあるか
GET  /rest/api/3/search/jql                       … 資料のラベルで既存の課題を検索
POST /rest/api/3/issue  × 10                      … エピック → 課題 → サブタスクの順に作成
GET  /rest/api/3/issue/PAY-4 → POST /rest/api/3/issueLink   … 既存のリンクを確かめてから作る（× 3）
```

`--apply` を付けないときは、POST をせず、GET（事前確認）だけをする。

### 事前確認（preflight）

1. **版の判定**: `serverInfo` の `deploymentType` が `Cloud` なら REST v3（説明は ADF という JSON の文書）。それ以外（Server、Data Center）なら v2（説明は Wiki 記法の文字列）
2. **課題タイプの対応づけ**（map_issue_types）。次の順で決める
   1. `--type-map` の指定
   2. 名前の一致（大文字小文字を無視）。epic = Epic・エピック、story = Story・ストーリー・User Story、task = Task・タスク、bug = Bug・バグ・不具合、subtask = Sub-task・Subtask・サブタスク
   3. 階層。epic = `hierarchyLevel` が 1、subtask = `subtask: true`、task = サブタスクでない階層 0 のもの
   4. story・bug が見つからなければ task で作り、その旨を警告する

   必要なタイプ（今回の計画で使うもの）が見つからなければ、何も書き込まずに止まる
3. **作成画面の項目**: タイプごとに createmeta を取り、そのタイプの画面にある項目（description、labels、priority、duedate など）と、必須の項目を知る。「Epic Name」「Epic Link」という名前の項目があれば、その id（`customfield_…`）を覚える（Data Center 用）

### 操作の一覧（plan_operations）

親が先にできるように、次の順に並べる。

1. すべてのエピック
2. すべての課題（エピックの ref を覚えておく）
3. すべてのサブタスク（親の課題の ref を覚えておく）
4. すべての依存のリンク（`A blocks B`）

### 1 件の課題の組み立て（build_fields）

**例: E1-1 を作るときに実際に送った fields（description 以外）**

```json
{"project": {"key": "PAY"},
 "issuetype": {"id": "10001"},
 "summary": "ユーザー認証をSSOに統一する",
 "labels": ["auth", "sso-login", "pptx2jira", "p2j-3588d9c599"],
 "duedate": "2026-11-30",
 "parent": {"key": "PAY-1"}}
```

| 項目 | 決め方 |
|---|---|
| summary | 要約（255 字で切る） |
| labels | 課題のラベル + `pptx2jira` + `p2j-<資料のハッシュの先頭 10 桁>`。最後のものが「どの資料から作ったか」の印で、二重登録の防止に使う。画面にラベルの項目がなければ付けない（警告を出す） |
| priority | 計画に優先度があり、プロジェクトの選択肢にあれば付ける。なければ付けずに警告 |
| duedate | 期限があり、画面に項目があれば付ける |
| 親 | サブタスクは `parent` = 親の課題。エピックの下の課題は、Cloud なら `parent` = エピック、Data Center なら Epic Link の項目 = エピック。Data Center のエピックには Epic Name の項目に要約を入れる |
| description | 次に示す Markdown を、Cloud なら ADF、Data Center なら Wiki 記法に変換したもの |

埋められない必須項目（プロジェクト独自の必須のカスタム項目など）があれば警告を出す。既定値がなければ、その課題の作成は Jira に拒否される。

**例: E1-1 の説明（変換前の Markdown）**

```markdown
社内管理画面と加盟店ポータルの認証を SSO に統一する。

### 受け入れ条件

- 社内管理画面と加盟店ポータルの両方で SSO ログインできる

### 出典と根拠

- 担当（資料の表記）: 認証チーム
- 資料から推測した項目: due_date（要確認）
- 出典: sample.pptx スライド 2

> ユーザー認証をSSOに統一する
> 期限は11月末
```

課題を開いた人が、どのスライドのどの文から作られたか、何が推測かを、その場で確かめられるようにしている。

### Markdown → ADF / Wiki 記法（md_convert.py）

1. Markdown を行ごとに見て、中間の木（見出し、段落、リスト、引用、コード、表）にする
   - リストは字下げの深さで入れ子にする。同じ深さで `-` と `1.` が切り替わったら、別のリストにする
   - 表は、2 行目が `|---|` の形なら表とみなす
2. 行の中の飾り（太字、斜体、コード、リンク、`<br>`）を変換する
3. 木を出力の形にする

| Markdown | ADF（Cloud） | Wiki 記法（Data Center） |
|---|---|---|
| `### 見出し` | `heading`（level 3） | `h3. 見出し` |
| `**太字**` | text + `strong` | `*太字*` |
| `*斜体*` | text + `em` | `_斜体_` |
| `` `コード` `` | text + `code` | `{{コード}}` |
| `[文字](URL)` | text + `link` | `[文字\|URL]` |
| `- 項目`（入れ子） | `bulletList` > `listItem` | `*`、`**` |
| `1. 項目` | `orderedList` | `#`、`##` |
| `> 引用` | `blockquote` | `{quote}…{quote}` |
| 表 | `table` > `tableRow` > `tableHeader` / `tableCell` | `\|\|見出し\|\|`、`\|セル\|` |
| `<br>` | `hardBreak` | `\\` |

Wiki 記法では、本文中の `{ } [ ] |` をエスケープする（意図しないマクロやリンクにならないように）。

### 二重登録の防止

同じコマンドを何度実行しても、同じ課題は 1 回しか作らない。

1. **状態ファイル**: 課題を 1 件作るたびに、`jira_state.json` に `ref → キー` を書き足して保存する（途中で止まっても、作った分は記録に残る）。リンクも `[blocker, blocked]` を記録する
2. **状態ファイルにない ref の拾い直し**（recover_state）: `project = "PAY" AND labels = "p2j-<ハッシュ>"` で検索する。見つかった課題を (正規化した要約, タイプ名) で索引にし、計画の課題と一致すれば、作らずにそのキーを使う。状態ファイルを消した・別の PC で実行した、という場合に効く
3. **リンク**: 作る前に、依存される側の課題の `issuelinks` を取り、相手が同じ Blocks のリンクが既にあれば作らない

**例: 実際の jira_state.json**

```json
{"project_key": "PAY",
 "created": {"E1": "PAY-1", "E2": "PAY-2", "E1-1": "PAY-3", "E1-2": "PAY-4", …, "E2-2-a": "PAY-10"},
 "links": [["E2-1", "E1-2"], ["E2-1", "E2-2"], ["E2-2", "E2-3"]]}
```

状態ファイルの `project_key` と、今回のプロジェクトが違えば止まる（別プロジェクトの記録を使わないため）。

### 失敗の扱い

| 状況 | 動き |
|---|---|
| 429（レート制限） | `Retry-After` の秒数（最低 1 秒）待って再試行 |
| 5xx・接続エラー | 2 秒から倍々（最大 60 秒）で待ち、最大 6 回 |
| 400 など | その課題をエラーとして記録し、次へ進む。Jira のエラーの文（`errorMessages` と `errors`）を残す |
| 親が作れなかった | その子（課題・サブタスク）は作らず、「親が作れなかった」と記録する |
| リンクの片方がない | リンクを作らず、エラーとして記録する |

エラーがあれば終了コード 1。原因を直して同じコマンドを流せば、作った分は飛ばして続きから作る。

### 添付（--attach-renders）

作った課題に、出典のスライドの画像（`renders/slide-NNN.png`、最大 3 枚）を添付する。Jira の添付 API が要求する `X-Atlassian-Token: no-check` を付けて送る。添付に失敗しても課題は残し、警告だけを出す。

## 8. こういうときどうなるか

| 状況 | 動き |
|---|---|
| LibreOffice がない | スライド画像なしで進む。VLM には内容の画像だけを送る。内容の画像もないスライドは `text_only` |
| vLLM が落ちている | 全スライドが `error_fallback`（抽出結果）。deck.md は作られる。スキルの手順では、ここで vLLM の状態を確かめる |
| VLM が行を落とした | やり直しで直れば `vlm_retry`、直らなければ `fallback`（本文は抽出結果、図の説明だけ VLM のもの） |
| VLM が数字を作った | 図の説明の外なら不合格。やり直し → だめなら `fallback` |
| VLM が表を崩した | 起きない。表の中身は抽出値で差し込むので、VLM は位置しか決めない |
| 資料を更新して同じ作業ディレクトリで抽出し直した | ハッシュが変わるので、古い md・renders・deck.md・vlm_report.json を消してから作り直す |
| md を手で直した | `--rebuild-deck` で deck.md だけ作り直す |
| Claude が資料にない課題を作った | 引用が資料にないので、検査でエラーになり登録できない |
| Claude が期限を推測で埋めた | `inferred_fields` にあれば説明に「要確認」と出る。申告がなく資料に数字もなければ、検査で警告 |
| 登録の途中で止まった | 同じコマンドを流すと、作った分は飛ばして続きから |
| 状態ファイルをなくした | 資料のラベルで検索して拾い直すので、二重には作らない |
| プロジェクトに Story がない | Task で作り、警告を出す |
| プロジェクト独自の必須項目がある | 警告を出す。既定値がなければ、その課題は Jira に拒否されてエラーとして記録される。子の課題も作らない |
| 担当者 | Jira のユーザーには割り当てない。資料の表記を説明に書く |
