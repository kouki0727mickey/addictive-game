# pptx2jira 設計の検討とレビューの記録

> 作成: 2026-10-25。対象: `extract.py` / `vlm_markdown.py` / `prompts/plan_issues.md`・`plan_issues.py` / `issues_schema.py` / `jira_push.py`・`md_convert.py` / スキル `/pptx-to-jira`・`/pptx-to-markdown`
> 各項目を 3 回ずつレビューした。各回は「実際に動かす → 出力を読む → 直す → テストに加える」で行った。
> 検証はすべて手元のサンプルの pptx と偽の vLLM・Jira・Claude API で行った。**実際の vLLM のモデル・Jira・Claude API ではまだ試していない**（環境に接続先と API キーがないため）。

## 1. 方式の検討（何を比べて、何を選んだか）

### 全体: 「VLM に全部読ませる」か「抽出を正本にして VLM で補う」か

| 案 | 長所 | 短所 |
|---|---|---|
| A. スライド画像だけを VLM に読ませる | 実装が簡単。見た目どおりの順序 | 文字の誤読・脱落・言い換え・数字の捏造を検出できない。表の桁ずれ |
| B. pptx のテキストだけ（VLM なし） | 文字は正確。速い・安い | 読む順序、矢印・図形の関係、画像の中身が分からない |
| **C. 抽出を正本 + VLM は構造と図だけ + 機械検査**（採用） | 文字の正確さと見た目の理解を両立。検査で VLM の失敗を拾い、B に戻せる | 実装が多い |

💡 C を選んだ理由: Jira の課題は数字（期限・性能目標）と固有名詞が命で、そこを VLM の読み取りに頼ると誤りを検出できない。pptx は文字を XML で持っているので、画像から読む必要がない。

### ① 抽出

- 読む順序: (a) 図形の (top, left) で並べる / (b) 図形の重なり順（z 順）/ **(c) 再帰 XY-cut**（採用）。(a) は 2 段組みで左右を交互に読み、(b) は作った順で意味がない。XY-cut は文書解析で定番の、空白の帯で再帰的に切る方法
- 結合セル: 起点だけに値を入れる案と、範囲に繰り返す案。**繰り返す**（採用。理由はレビュー①-2）
- スライド画像: python-pptx には描画機能がないので LibreOffice（PDF 経由）。非表示スライドも PDF に出してページとスライドの対応を保つ

### ② Markdown 化

- 文字の扱い: 「抽出テキストを渡して清書させる」（採用）。VLM が原文から外れたかを網羅率で測れる
- 表・グラフ: VLM に書かせる案と、**位置だけ決めさせて抽出値を差し込む案**（採用。②-3）
- 失敗時: そのスライドだけ抽出結果に戻す（全体を止めない）

### ③ 課題の計画

- 作り手: **Claude Code 自身（スキルの既定）** と `plan_issues.py`（API。一括処理・CI 用）。指示は `prompts/plan_issues.md` に 1 つだけ置き、両方で使う
- 出力の固定: 構造化出力（JSON スキーマ）。スキーマは構造化出力の制約に合わせ、null を使わず空文字、全項目 required
- 作り話の抑止: 課題ごとに資料の引用（evidence）を必須にし、引用が資料にあるかを機械で確かめる。推測した項目は `inferred_fields` に申告させる

### ④ Jira 登録

- 経路: REST API を直接（採用）と Atlassian のコネクタ（MCP）。REST なら二重登録の防止・再開・添付・Data Center 対応を自分で保証できる。コネクタしかない環境向けの手順はスキルに書いた
- 二重登録の防止: 状態ファイル + 資料ごとのラベルでの検索。Jira の課題プロパティを JQL で検索する案は、アプリで索引を宣言しないと検索できないので見送った

## 2. レビューの記録

### ① 抽出（extract.py）

| 回 | 見つけたこと | 直したこと |
|---|---|---|
| 1 | 2 段組みのスライドを「左の見出し → 右の見出し → 左の本文 → 右の本文」と読んだ（XY-cut が常に上下を先に切っていた）。表のセルを読む所に意味のない行が残っていた。サンプルの結合セルの作り方が誤っていた（python-pptx の merge は中身を連結する）。行頭の `#` や `1.` が Markdown の見出し・リストに化ける。題のないグラフが「無題」 | 上下・左右で最も広い空白の帯を比べて広い方で切る。不要な行を削除。サンプルを修正。行頭のエスケープ。系列が 1 つなら系列名を題にする |
| 2 | 横長のスライドでは座標の比のままだと左右の空白が小さく見える。入れ子の番号付きリストで、親が進んでも子の番号が続く。結合セルを起点だけに入れると、行ごとに読んだとき「実装の担当」が空になる（課題の担当が落ちる）。タイトルをテキストボックスで書いたスライドが「タイトルなし」になる | 左右の空白をスライドの縦横比で実際の幅に直して比べる。親の番号が進んだら子を振り直す。結合範囲に値を繰り返し、範囲は `merged` に残す。上部の短い 1 段落の箱を題とみなす（`title_guessed`） |
| 3 | 画像の判定に `hasattr(shape, "image")` を使っており、中身のない画像プレースホルダで例外が漏れうる（`hasattr` は AttributeError 以外を握りつぶさない）。同じ作業ディレクトリで別の資料を抽出すると、前の資料の Markdown が混ざる。箇条書きの直後の普通の段落が、リスト項目の続きとして読まれる。80 枚の資料で速度を確認（抽出と描画で約 21 秒） | `isinstance(shape, Picture)` に変更。資料のハッシュが変わったら `md/`・`renders/`・`deck.md`・`vlm_report.json` を消す。箇条書きから普通の段落に変わる所に空行を入れる。SmartArt・XY-cut・グループ座標・結合セルなどをテストに追加 |

### ② Markdown 化（vlm_markdown.py）

| 回 | 見つけたこと | 直したこと |
|---|---|---|
| 1 | 偽の「理想の VLM」でも全スライドが不合格になった。原因は 3 つ: タイトル（見出しはこちらで付ける）を網羅率の分母に入れていた、リンクの URL が比較の邪魔をした、画像のファイル名（ハッシュ）の数字とグラフの値 `12.0` を「作られた数字」と誤判定した | タイトルを分母から外す。比較の前にリンク先・画像のパス・コメントを除く。`12.0` と `12` を同じに扱う |
| 2 | 原文にない数字を出しても「合格」になっていた。やり直しの指示が抜けた行しか伝えていなかった。複数回試したとき、網羅率だけで採用していた | 作られた数字も不合格の条件に。やり直しの指示に抜け・作られた数字を両方書く。合格した試行を優先して採用 |
| 3 | 表とグラフを VLM に書かせると、値の検査ができない（グラフの値は網羅率の単位に入らない）。手で直した md から deck.md を作り直す手段がない | 表・グラフは `{{TABLE-n}}` の位置だけ書かせて抽出値を差し込む（置き忘れは末尾に、存在しない id は消す）。`--rebuild-deck` を追加 |
| 追加（スキルの通し実行で発見） | VLM が画像の説明を丸ごと落としても、網羅率（文字だけ）では合格になる | 送った画像ごとに `> 図（IMG-n）: ` の説明を要求し、欠けたら不合格（`missing_figures`）。fallback では、どの試行のものでも最も長い図の説明を残す |

### ③ 課題の計画（prompts/plan_issues.md・plan_issues.py）

| 回 | 見つけたこと | 直したこと |
|---|---|---|
| 1 | 構造化出力のスキーマで null・任意項目を使うと制約に触れうる。根拠のない課題を機械で見分けられない | null を使わず空文字、全 object に `additionalProperties: false` と全項目 required（テストで再帰的に確認）。evidence（原文の引用）を必須に |
| 2 | Haiku 4.5 は `effort` を受け付けない。server-side fallback は対応モデルだけ。費用の上限がない | モデルごとに引数を組み立てる。呼ぶ前に `count_tokens` で見積もり、`--max-usd` を超えたら呼ばない。`--dry-run` |
| 3 | 偽の API サーバーで SDK を通して確認したところ、`--review-pass` の 2 回目で資料が再びキャッシュされずに課金される形だった。指示が説明欄に「出典: スライド n」を書かせ、登録時に付ける出典と重複した | 資料を独立したブロックにして `cache_control` を付け、2 回目も同じブロックを先頭に置く。説明欄に出典を書かせない |

### 検査（issues_schema.py）

| 回 | 見つけたこと | 直したこと |
|---|---|---|
| 1 | 引用を資料全体で探すと、別スライドの文で「根拠あり」になる | 出典のスライドで探し、なければ資料全体で探す（別スライドにあれば警告、どこにもなければエラー） |
| 2 | 空白入りのラベルが検査を素通りした（Jira は拒否する）。期限の推測を見分けられない | ラベルをエラーに（`--fix` で直せる）。推測でない期限は月か日の数字が資料にあるかを見る |
| 3 | 「300ms → 200ms」のような要約・受け入れ条件の数字の書き換えを拾えない。テスト用の課題案にわざと残した誤り（資料は「11月〜12月」なのに「11月に実装する」というサブタスク）は機械では拾えず、スキルの見直し手順で落とした | 要約・受け入れ条件の数字が出典にない場合を警告に。言い換えの検出は機械では限界があるので、スキルの手順 3-4 の見直し観点に明記 |

### ④ Jira 登録（jira_push.py・md_convert.py）

| 回 | 見つけたこと | 直したこと |
|---|---|---|
| 1 | Cloud（v3）は説明に ADF が要り、Data Center（v2）は文字列。日本語のプロジェクトでは課題タイプが「エピック」「サブタスク」。Data Center ではエピックに Epic Name が必須 | `serverInfo` で版を判定し、ADF と Wiki 記法の変換器を作る。タイプは名前 → 階層の順で対応づけ。Epic Name / Epic Link を createmeta から探して使う |
| 2 | Markdown 変換で、箇条書きの直後の番号付きリストが箇条書きに吸収された。`Retry-After: 0` で待たずに再試行を繰り返す | 同じ深さで記号の種類が変わったら別のリストに。待ち時間を最低 1 秒に |
| 3 | 状態ファイルを消して再実行すると、課題は拾い直せたが依存のリンクを二重に作った。親のエピックの作成に失敗したときの子の扱いが未検証 | リンクを作る前に、課題の既存リンクを確かめる。親が作れなかった子は作らないことをテストで確認（エピック 1 つを失敗させ、その子 4 件が作られないこと） |

### スキル（/pptx-to-jira・/pptx-to-markdown）

| 回 | 見つけたこと | 直したこと |
|---|---|---|
| 1（読み直し） | スキーマの表示に意味のない引数が要った。手で直した md を反映する手順が「md を消して VLM を流し直す」になっていた（直した内容が消える）。依存の一覧がない。作業ディレクトリが資料の中身ごとコミットされうる | `--print-schema` を単独で使えるように。`--rebuild-deck` の手順に変更。`requirements.txt` を追加。`p2j-work/` を `.gitignore` に |
| 2（書いてあるとおりに通し実行） | 抽出 → Markdown 化（偽 vLLM）→ 計画（このセッションの Claude が指示どおりに作成・見直し）→ 検査 → 予定の表示 → 事前確認 → 登録（偽 Jira）まで通った。途中で、画像の説明の欠落が検出されないこと（②の追加）と、説明欄の出典の重複（③-3）が見つかった | それぞれの段階で修正 |
| 3（読み直し） | 確かめる対象に `missing_figures` と `error_fallback` が抜けていた。vLLM なしで deck.md に直接書き足した後に `--rebuild-deck` を使うと書き足しが消える | 手順 2 に追記 |
